多语言智能客服：先理解问题，再组织回复

平台 v6 · 客服契约 support-v1 · 2026-11-02

这是同级 Agent 案例。当前以中、英、西、日四语有限规则与模板运行，未调用语言模型，未连接真实渠道或订单系统。所有回复只记录到模拟收件箱；不是生产客服服务。

演示步骤

  1. 在 Agent 治理中选择「多语言智能客服」，进入编排画布。也可新建 Agent，选择同名模板，创建自己的完整契约与独立画布。
  2. 双击「选择回复策略」编辑 hybrid / combined / per_intent；双击「启用等待回应」编辑首响、进度和转人工阈值。保存画布。
  3. 打开运行参数，点击「填入新的四语样例」，校验并运行。每次生成新的虚构会话ID，避免与待人工会话冲突。
  4. 中文重复物流问题会归并，洗护先答；英文两个FAQ先合并答复；西语请求人工直接建单；日语缺订单号先澄清。中文订单核对延迟后补充答复。
  5. 进入「模拟客服收件箱」，看原声、意图与真实生成时间。西语人工单可填写西语答复；点击记录后生成模拟人工回复、完成工单。
  6. 要演示等待提醒：将查询延迟改为12000ms；要演示超时：设延迟25000ms，超过默认20秒转人工，停止自动业务结论。保存后用新会话样例运行。

为什么这样编排

同一个客户可能连续发送“订单在哪”“还没到”“另外怎么洗”。逐条回答会重复打扰，也可能漏问题。先隔离客户、保留消息ID，再按意图与订单归并，就可以把两个物流催问作为一个待答问题，把洗护作为另一个问题。明确的问题先答，慢查询保留在待办中。

窗口只归并当前提交的批次快照；演示没有实时消息入口，窗口期间新发到外部渠道的消息不会被自动收集。后续批次必须使用新batch_id，稳定保留conversation_id与message_id。处理中的会话和未完成人工单阻止并发自动回复，避免机器人与人工同时答复。

模式行为适用情况
combined 汇总同一会话的答案合并输出；澄清与人工动作单列多个关联问题，客户希望一次看完
per_intent 逐意图每个归并问题一条回复，而非每条原声一条多订单或每个问题需独立跟进
hybrid 混合（默认）有依据的FAQ先答，剩余查询后汇总；已答不重复快慢混合，降低客户等待焦虑
auto 自动超过2个意图汇总，否则混合（演示启发规则）展示策略路由，生产需重新校准

明确人工、语言不支持和缺少必要资料可以提前走安全模板出口；不会被其他客户的慢查询拖住。退款、取消、改址、补偿只登记人工核实，不自动执行或承诺成功。

19个节点的画布

开始 → 接入去重 → 语言 → 窗口归并 → 意图风险 → 策略 → 等待配置 → 快捷分支 → 知识/订单核对 → 组织答案 → 质量门禁 → 分批输出 → 人工分支 → 会话报告 → 结束。快捷、质量失败与人工分支各有独立节点。

节点作用
接入校验与消息去重按客户会话隔离，保留原文和历史
识别回复语言明确偏好优先，未知语言转人工
短窗口归并消息合并输入批次内碎片，不把历史已答消息重新回答
识别意图与风险一条多意图、重复问题归并、订单分别处理
选择回复策略汇总/逐项/混合；人工请求优先
启用等待回应首响与进度独立计时，限频并可超时转人工
先答明确问题只用核实的演示FAQ，随后不重复
核对知识与订单使用运营提供的演示事实；无真实业务API
组织多语言答案按意图覆盖组装，保留引用来源
校验覆盖与承诺检查语言、来源、缺漏与业务承诺
保守回退校验失败仅澄清或转人工
分批输出回复模拟投递、幂等；安抚不算解决
创建人工接管单携带原声、已答、待答和优先级
汇总会话报告逐会话结果、回复序列与等待指标

等待计时器从服务端收到请求即启用，画布中的等待节点承载配置与状态展示。因此即使在队列中，也能发出提醒。它与主处理流程独立运行，取消后立即停止。质量检查当前是结构、覆盖和来源检查，不是通用语义审核。

输入Schema怎么写

batch_id表示这次提交；conversations[]按客户会话隔离；messages[]保留原声与顺序。message_id在同会话中稳定且唯一；role=agent或answered=true只作上下文。preferred_language优先于识别，未知语言用英文说明并转人工。order_ref明确关联订单，business_context.orders只能放运营已核实的虚构事实，不能把客户猜测当查单结果。

同批次ID与内容重复提交返回原运行；同ID不同内容拒绝。不同订单按不同意图组处理。纯附件不自动读图，进入人工核实。历史记录只用于去重与追溯，演示规则不具备通用上下文推理能力。

输出JSON保留什么

字段产品含义
conversations[].intents[]code/summary/order_ref；message_ids/evidence追溯原声；status/source_ids说明问题是否已有答复与依据
conversations[].replies[]kind/language/text；intent_ids覆盖意图；source_message_ids/source_ids追溯；emitted_at记录实际投递时间
state / handoff_ticket_id已答、待澄清、待人工、无新消息、取消；人工单独立于运行完成状态
metrics首响、首个实质回答、等待提醒数、已答意图与总意图
provenance / limitations规则执行器、Prompt版本、模型/渠道连接情况与限制

answered表示系统提供了答复，不能当作客户确认解决。会话人工处理后更新收件箱；原运行输出保持结束时快照，便于复盘。运行追踪与收件箱可查看实际完整JSON。

指标与产品取舍

  • 首响时间：从接入到任何第一条回复，衡量客户是否被及时回应；安抚也算。
  • 首次实质回答时间：只统计有依据的快捷答案或完整答复；澄清、安抚、转人工不算。
  • 意图覆盖：已提供答复的意图 / 归并后的全部意图；没有把重复原声放大成多个问题。
  • 等待提醒次数：每会话最多两条等待提醒，避免反复打扰；超时人工提示另计。
  • 生产还应看客户确认解决率、重开率、人工接管率、P95延迟、模型/工具失败率和每个有效解决的成本。当前样例没有这些业务证据，不编造指标值。

主要难点是快慢问题混合时既不能让客户一直等，也不能提前编造答案。产品手段是意图台账、明确问题先答、独立等待计时、来源门禁和携带上下文的人工接管。等待反馈与问题解决分开计量，才不会用大量“收到”掩盖低解决率。
